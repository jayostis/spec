# spec/CHANGELOG.md

Top-level changelog for the Cascade Protocol vocabulary specifications. Per-vocab changelogs live in `ontologies/<vocab>/CHANGELOG.md`. This file summarizes cross-vocab milestones.

Format: each entry is one milestone, dated, with a short prose summary and pointers to the per-vocab changelogs that go with it.

## 2026-09-02: Three of seven published contexts could not be loaded at all (no vocabulary version moves)

**No term is added, removed or renamed, no ontology file is touched, and no shape changes.** Eight keys are deleted from `contexts/v1/cascade.jsonld`, `core.jsonld` and `health.jsonld`, and a new `contexts` CI workflow asserts that every published context loads. `VOCAB_VERSIONS` is unchanged, deliberately: the vocabularies did not move, their published mapping did.

**Every non-keyword key in a `@context` is a term definition, so a section header written as one is a term whose IRI is prose.** `"__comment_core": "=== Core Vocabulary (cascade:) ==="` is not a comment a processor skips — JSON-LD has no comment syntax — and a conformant processor rejects **the entire file** over it rather than the one entry. 716 terms in `cascade.jsonld` were unreachable because six of them were headings; `core.jsonld` and `health.jsonld` carried one each, written as release notes. `checkup`, `clinical`, `coverage` and `pots` were never sectioned and were never affected.

**It survived because nothing had ever passed these files to a processor.** `json.load` succeeds on all seven — they are valid *JSON*, so an editor, a linter and a JSON syntax check all report them fine. Only expansion objects. `conformance/scripts/run_conformance.py` is pure Turtle and never touches a context; no script under `scripts/` opened `contexts/`; `sdk-typescript` cites them in `@see` comments and hand-writes its own context in `src/jsonld/context.ts`. The files were published, were the normative mapping [#4](https://github.com/jayostis/spec/issues/4) proposes to make them, and had never been read by the kind of consumer that proposal invites. Found while building a downstream converter that reads them as its only source of serialization rules — the first attempt to load them with a real processor.

**Deleted rather than re-keyed to `@comment`, on evidence rather than taste.** A processor ignores an `@`-prefixed key only when what follows the `@` is *letters only*: `@comment` and `@commentCore` are ignored, while `@comment_core` and `@comment1` fail with the identical error to the original, in both JSON-LD 1.0 and 1.1 processing modes. The obvious rescue — keep the name, prepend an `@` — leaves the file exactly as broken, and six sections cannot all be `@comment` because JSON keys are unique. Nothing is lost by deleting: the six in `cascade.jsonld` restate the prefix carried by every term beneath them, and the two version notes duplicate the ontology changelog, where `_comment_v3_4` is the one-line version of `core.ttl`'s `# Version 3.4 (2026-08-03)` block. Controls 3 and 4 of the new suite pin both halves of the naming rule so it does not have to be rediscovered.

**The check deliberately does not use `rdflib`, and that is the part worth reading before changing it.** rdflib is already pinned here and parses JSON-LD, so it is the obvious instrument; it also accepted all three broken files without complaint. A check built on it would have been green over the exact defect it exists to catch, which is the same shape of vacuous pass that `check-class-coverage.py` exists to prevent elsewhere in this repository. `PyLD==3.3.0` is pinned separately in `scripts/requirements.txt`, and control 6 of `scripts/test-check-context-validity.sh` fails if the two are ever consolidated. Because a processor reports the first error and stops without naming the term responsible, the check re-tests each term in isolation on failure and names every culprit.

**What the check does not assert.** It asserts that a context **loads**, never that a term maps to the *right* IRI. A context resolving a term to the wrong predicate is valid JSON-LD and passes. That question is [#46](https://github.com/jayostis/spec/issues/46), [#47](https://github.com/jayostis/spec/issues/47) and [#44](https://github.com/jayostis/spec/issues/44), all of which change term definitions and all of which were blocked on this: a consumer could not resolve anything in the three largest contexts, because it could not load them. `CONTRIBUTING.md` gains the two commands — nine must be green before review, not seven. See jayostis/spec#48.

## 2026-09-01: Seven classes were invisible to the gate that judges them (core v3.12, coverage v1.8, checkup v3.4, workbench v1-draft.0.8)

**No term is added, removed or renamed, and no shape changes.** Seven classes gain `rdfs:subClassOf prov:Entity`: `coverage:BenefitStatement`, `coverage:ClaimRecord`, `cascade:AIDiscardedExtraction`, `checkup:CheckInSettings`, `workbench:Hypothesis`, `cascade:ConflictDetail` and `workbench:Pin`. Four vocabularies move together because it is one change with one argument.

**The defect was a hole in a gate, of the shape that makes a green run meaningless.** In this specification `rdfs:subClassOf prov:Entity` asserts that instances of a class are stored record data, and `scripts/check-class-coverage.py` reads that chain to decide which classes it examines. All seven carry their own data properties and hold record data; none declared any superclass at all. So the gate did not report them as unshaped — it never looked at them, reported PASS, and they were absent from `scripts/known-unshaped-classes.json` too, because that file is the gate's *output* and not a filter on it. **Invisible in both directions:** a class the gate cannot see is neither judged nor recorded as owing a judgement, and the check that exists to catch vacuous `conforms:true` was itself returning one. `conformance/KNOWN_FAILURES.json` had been carrying two of them — `coverage:ClaimRecord` and `coverage:BenefitStatement` — as UNSHAPED with `ownedBy: spec` for months: a downstream repository reporting a gap this repository's own gate could not.

**The fix is in the vocabulary, not in the check, and that distinction is the whole design.** Pointing the check at every class with no `rdfs:subClassOf` reports 57 unshaped classes, of which 43 are value enumerations — `evidence:VerdictValue`, `diabetes:MealType`, `genomics:ZygosityValue` and 40 more, each with zero properties and each the range of some predicate. Baselining those would record 43 obligations that can never be discharged, because a code-list member has nothing for a shape to constrain — verbatim the defect jayostis/spec#12 removed for eleven terms when `cascade:DataProvenance` and its ten values lost a `prov:Entity` claim they should never have made. So each of the seven is argued individually, from its own properties: `coverage:BenefitStatement` is the domain of nine and the range of none; `checkup:CheckInSettings` holds a schedule the patient chose; `cascade:ConflictDetail`'s blank-node addressing governs how it is named, not whether it is stored.

**No shape is written, deliberately, and that is recorded rather than hidden.** What each class requires is a separate per-class judgement — `coverage:BenefitStatement` alone has nine properties, four of them `xsd:decimal` money fields including `patientResponsibility` — and a hurried shape would record it wrongly. All seven go into `scripts/known-unshaped-classes.json`, which grows from 34 entries to 41. **That growth is the point: the debt did not increase, it became visible.** `shaped` is unchanged at 69, the list can still only shrink, and nothing in it is acceptable in the long run.

**A new CI gate asserts the vocabulary fact, not the check.** `scripts/test-record-class-declarations.sh` runs in the `shapes` workflow beside `test-check-class-coverage.sh` and uses `check-class-coverage.py` unchanged as its instrument. It requires each of the seven to be in the population, requires the 43 value enumerations to stay out, and pins the population at 110 record classes and 69 shaped — so widening the check's scope over the enumerations fails here rather than shipping. It reads the population directly rather than the unshaped list, so discharging a baseline entry does not turn it red with a false diagnosis and complete shape coverage does not turn it red at all. `CONTRIBUTING.md` lists it: seven commands must be green before review, not six.

**Strictly additive at validation time.** No shape targets `prov:Entity`, so no record's verdict changes under an entailing validator either; `scripts/check-shape-targets.py` is green, which is what establishes it. `workbench:Investigation` meets the same test and is deliberately left undeclared — jayostis/spec#13 did not scope it, and it needs its own issue. See `ontologies/core/CHANGELOG.md`, `ontologies/workbench/CHANGELOG.md`, `PENDING_DOWNSTREAM_SYNC.md` and jayostis/spec#13.

## 2026-09-01: The ratified consent scope list, and only the value set demoted (core v3.11, core shapes v1.9)

The first vocabulary change to follow D-CONSENT-1, and it corrects the release that preceded it by a day. core v3.10 published `cascade:ConsentScope` as a **closed** one-member enumeration at `sh:Violation`; D-CONSENT-1 ratified the list as `social-history` / `substance-use` / `mental-health` and ratified it **OPEN** — *"`sh:in` at `sh:Warning` at most, never `sh:Violation`"*, because *"a closed list missing a member rejects conformant data"*. A record tagged substance-use or mental-health was rejected by `spec` as shipped. `cascade:SubstanceUseConsent` and `cascade:MentalHealthConsent` are added as `cascade:ConsentScope` named individuals, and `cascade:ConsentScopeShape`'s single property block **splits**: `sh:nodeKind` / `sh:minCount` / `sh:maxCount` keep `sh:Violation`, `sh:in` moves to `sh:Warning` in a block of its own — because the ratification demotes the *value set*, not "two consent scopes on one record". Nothing reaches the shape by `sh:node`, so the Warning is delivered as a Warning and `scripts/known-severity-escalations.json` is unchanged. `scripts/check-nested-severity.py`, this repository's standing gate for rule S5, reports the shape clean, and that is what establishes the precondition. It establishes nothing beyond it: the membership, the severity and the block split are asserted by no check in this repository, because `spec` runs no SHACL validator. Their proof is behavioural, and it belongs to `conformance` as the `manual` verification in jayostis/spec#38 declares. Strictly more permissive: no value that conformed under v3.10 fails under v3.11, and no presence constraint is added anywhere. See `ontologies/core/CHANGELOG.md` and jayostis/spec#38.

## 2026-09-01: Consent architecture ratified as D-CONSENT-1 (pod-structure 1.4, first decisions/ entry)

No vocabulary change yet. An external contributor's archaeology (jayostis/spec#20) found three half-built, apparently conflicting statements about where consent lives, and correctly refused to build against any of them. The answer is recorded in `decisions/2026-09-01-consent-architecture.md` — the first entry in a new `decisions/` directory, created because the contributor did careful work and still reconstructed the history backwards: the design intent lived in private repositories. Decisions of this kind are now recorded in the public authority repo.

Short form: `cascade:consentScope` was designed in the SDKs (2026-03) and its ontology declaration never landed — it is to be declared as an ObjectProperty over an OPEN `cascade:ConsentScope` value set (`social-history`, `substance-use`, `mental-health`; never closed at sh:Violation). ODRL is rejected — Solid-era scaffolding with no enforcer anywhere in the stack; consent STATE will be modelled on FHIR Consent as a future `cascade:ConsentRecord` in `consents/`, deliberately not built until it has a consumer. Scope-on-the-record is a data-sensitivity tag, the pod path is ACL container mechanics, consent state lives in `consents/`, and `provenance/` holds disclosure receipts only. `pod-structure.md` goes to 1.4: the `consents/` reservation is re-described accordingly and the ODRL wording is removed.

## 2026-08-31: The Pod structure spec had forked, and neither copy was whole (pod-structure 1.3)

No vocabulary change. `pod-structure.md` goes to 1.3, and this entry records a reconciliation rather than new design.

**The document existed in two versions that had each received a real revision the other lacked.** The copy here was the only one to get section 4.3 (`attachments/`, core v3.7), section 7.5, and the v1.2 digest-and-encryption rules. The published copy at `cascadeprotocol.org/docs/spec/` was the only one to get the 2026-08-03 correction pass, which checked every `solid:forClass` registration and file/class table against the published ontologies and the reference patient pod and fixed fourteen phantom class names — so the copy in this repository, the authority, went on prescribing `clinical:MedicationRecord`, `cascade:HealthData`, `health:HeartRateStatistics`, `pots:POTSTest` and their siblings, names no Cascade ontology defines and no implementation writes, in registration examples an implementer would copy. Both copies said `Version: 1.1`. The published copy also documented `settings/preferences` and `profile/extended.ttl` — real, implemented structure (the reference pod contains both) that this copy never mentioned, including the rule that `solid:privateTypeIndex` MUST NOT appear in the publicly-readable `card.ttl`.

**v1.3 is the merge, verified rather than assumed.** Every disputed class name was checked against the ontology files in this repository and against the reference pod before choosing a side; the published copy's names won everywhere the two disagreed, and its warning that `clinical:ScreeningResult` / `clinical:DiagnosticResult` remain unratified is kept. From this side, v1.3 keeps sections 4.3 and 7.5, the digest rules, the Workbench `notes/` and `annotations/` containers, and the `/attachments/` ACL guidance. The two files are now byte-identical, `spec/` remains the authority, and the published copy is brought under `sync-from-spec.sh` so the fork cannot recur silently.

## 2026-08-31: Which bytes an attachment's digest commits to (pod-structure 1.2)

No vocabulary change: no term is added, removed or renamed, and no shape moves. One prose amendment to `pod-structure.md`, which goes to 1.2.

**Section 4.3 stated two rules that stop being compatible once a Pod is encrypted.** The attachment filename is a digest of the file's bytes, and content addressing is justified on a consumer hashing what it read and comparing it with where it read it from. The same section requires attachments to carry the same at-rest protection as record files. After encryption the bytes on disk are ciphertext while the name was computed from the plaintext, so a reader following the text literally finds a mismatch on every attachment: the section's own MUST breaks the section's own verification rule, and nothing said which reading was intended. Two implementations would have guessed differently, and the question was live because a DICOM importer is about to become the first writer of an attachment anywhere in the ecosystem.

**Settled as digest-of-plaintext, verified after decrypt,** under a new "Digest and encryption" subsection, with the naming rule restated in section 7.5. Encrypting or decrypting a Pod MUST NOT rename an attachment, and the `cascade:Attachment` node is identical in both states: encryption changes file contents, never the graph.

Naming the ciphertext was the alternative and is rejected in the text, because authenticated encryption uses a fresh nonce per operation and the same document sealed twice would get a different name. Deduplication and idempotent re-import would stop working, which are the two properties content addressing exists to provide; re-keying would become a rewrite of every `cascade:attachmentPath` and `cascade:contentHash` in the Pod, putting graph mutation on the key-rotation path; and one Pod would have two graphs depending on whether it was encrypted when read. Deriving the nonce from the plaintext to make ciphertext deterministic would recover the first two and is not permitted, because it makes the exposure below structural.

**The cost is named rather than hidden.** A plaintext digest is a known-plaintext oracle: a holder of the encrypted Pod who already has a document byte-for-byte can confirm its presence without decrypting. It discloses nothing about content the holder lacks, and personalised attachments make an exact-byte match unlikely without prior possession. Per-Pod digest salting is permitted as an escape hatch, MUST be declared, and costs cross-Pod deduplication.

Nothing implements `attachments/` yet, so no Pod migrates and the convention is set rather than changed.

## 2026-08-31: A value with no property to carry it (core v3.10)

Three terms, and the argument is about which two of them a validator will ever read. `cascade:consentScope` appeared exactly once in this repository — inside `cascade:proxyScope`'s `rdfs:comment`, which calls it a live, composable sibling — and was declared nowhere: no property declaration, no domain, no range, and no `sh:path` in any of the six stable shapes files. core v3.10 declares it as an `owl:ObjectProperty`, gives its value a code-list class (`cascade:ConsentScope`) to belong to, and constrains it in `core.shapes.ttl` v1.8.

**A stale comment would not be worth a release; a declared value with nowhere to live is.** `cascade:SocialHistoryConsent` has been declared since core v3.0 as "consent scope for social history data", labelled, commented with the regulation it exists for, and published in `contexts/v1/core.jsonld` — a value of a consent-scope property, with no property it could be the object of. `clinical.ttl` states the obligation outright: `clinical:SocialHistoryRecord` "requires separate consent scope (`cascade:SocialHistoryConsent`)". The requirement was stated in one file and unmeetable in every other. Downstream the cost is measurable: `sdk-typescript` carries `cascade:consentScope` as a predicate in its `TYPE_MAPPING` and silently drops the field on serialization because the predicate is unregistered, and its consent module — `applyConsent`, `clinicalOnlyPolicy`, `noAccessPolicy` — is pure in-memory filtering that writes no RDF at all. That is not a defect there. There was no predicate for it to write, so consent scope was enforced by application code and left no trace in the graph, and a consumer reading a pod could not determine what scope applied to a record.

**The form was decided on this repository's own evidence, not on taste.** An `owl:DatatypeProperty` would have left the existing value declared, labelled and pointed at by nothing — the exact condition being fixed. Thirteen of the fourteen named individuals in `core.ttl` already declare their value-class, and `cascade:SocialHistoryConsent` was the only orphan; the section header has read "Consent Scopes", plural, since v3.0, so the code list was intended from the start and only the class was never written. `cascade:proxyScope`'s own enumeration — `'full'`, `'read-only'`, `'investigation-only'`, listed in prose — is the anti-pattern rather than the precedent, and is deliberately left alone as a separate finding: an enumeration nothing can check is one a document can contradict.

**`sh:in`, not `sh:class`, and the draft that had `sh:class` could never have passed.** SHACL resolves class membership over the data graph. A pod record carries the value IRI and no `rdf:type` triple for it, because the type assertion lives in the ontology; nor is it rescued by a validator that merges one, since `conformance`'s runner builds its ontology graph from `rdfs:subClassOf` triples only. `sh:class cascade:ConsentScope` would have fired on every correctly-authored record, at `sh:Violation`. This repository has already paid for that mistake once, at one severity lower: clinical shapes v1.11 removed the `sh:class` constraints from `HasEncounterEdgeShape` and `LinkedConditionEdgeShape` because a value whose type lives outside the validated file "could never satisfy `sh:class` — it produced a Warning on every well-formed, fully-resolving edge and none on a malformed one." What follows is worth stating plainly: **`cascade:ConsentScope` does no validation work.** It earns its place on the 13-of-14 house-pattern argument, an ontology-consistency change; `sh:in` is what a validator actually reads. Both are wanted and only one is load-bearing.

**The class takes no PROV superclass, and that is the assertion the one automated check here can make.** A code list is not record data. `rdfs:subClassOf prov:Entity` would enter `cascade:ConsentScope` into `scripts/check-class-coverage.py`'s population, and the only ways to green the gate again would be to write a shape for a code list — which has nothing to constrain — or to baseline it, which `known-unshaped-classes.json` itself calls "an admission, not a fix". That is precisely why jayostis/spec#12 removed the axiom from `cascade:DataProvenance` and its ten value terms in core v3.9. The check passes at 103 classes examined, 69 shaped, 34 baselined, with the baseline file unmodified.

**This release constrains the value and never the presence, which is the ratchet holding rather than being described.** The obvious next move — `sh:minCount 1` on `clinical:SocialHistoryRecordShape`, since `clinical.ttl` states the obligation in prose — is three ratchet steps at once, and the ratchet has been written down since core v3.5: requiring presence the moment a property is defined turns every existing pod amber for something no producer has had the opportunity to write, and a warning that fires on correct historical data is a warning readers learn to skip. Step 2 is that `minCount` at `sh:Warning`, once the reference producers emit a scope; step 3 raises it to `sh:Violation` after a release in which the Warning is observably absent from conforming output. Each is its own vocabulary version. So `ontologies/clinical/` is untouched here and `clinical` in `VOCAB_VERSIONS` is unchanged — with the constraint living in `core.shapes.ttl`, where core-namespace properties are constrained, there is nothing for a clinical bump to describe. No follow-on issue is filed for step 2 either: its precondition does not hold, and a dispatchable issue that cannot be started is noise.

**Compatibility.** Purely additive, and no existing pod, fixture or reference record changes verdict: the shape evaluates only subjects that already carry the predicate, and none do. `conformance`'s `fixtures/clinical/social-history-smoking.ttl` carries no consent scope and keeps passing untouched — which jayostis/conformance#7 will assert rather than assume, alongside a positive fixture carrying the scope and a negative one carrying a non-scope IRI. `spec` runs no SHACL validator, so the durable form of graphs 1–3 is that fixture set.

**What is deliberately still open.** A `cascade:ConsentRecord` class, with the `consentGrantedAt` and `consentRevokedAt` that `sdk-typescript` models, is not here. A scope value cannot carry them — an individual is a singleton, so it has nowhere to put per-instance grant and revocation timestamps — and whether an audit trail of grant and withdrawal is *required* is a 42 CFR Part 2 question about required fields rather than an RDF modelling one. `pod-structure.md` reserves `consents/` for ODRL policies and `provenance/` for an audit trail, so such a class may want a different home entirely. jayostis/spec#20 carries it and is not dispatchable until someone who can speak to the regulation answers. Splitting it out is what let the unambiguous half — a value with no property, which no reading of Part 2 makes correct — land without waiting.

## 2026-08-31: A declared property no shape had an `sh:path` for (coverage v1.7)

One `sh:property` block. `coverage:sourceRecordId` has been declared since coverage v1.3 and constrained by nothing since, so a record carrying it had that field judged by nothing — the predicate-level form of the defect clinical v1.18 fixed at class level.

**It went unseen because it had nowhere to live.** The property was authored for `coverage:ClaimRecord` and `coverage:BenefitStatement`, and a property constraint lives inside a class's node shape, so with neither class shaped there was no node shape to put it in. The gap sat inside a larger one. What made it visible is that a *different* class started carrying the property: the declaration is deliberately domain-free, so `coverage:InsurancePlan` — which does have shapes — may carry it and does, in `conformance`'s `coverage-001` and in `reference-patient-pod/clinical/insurance.ttl`.

**This is transcription, not design.** `health:sourceRecordId` and `clinical:sourceRecordId` already carry the identical constraint six times over — `xsd:string`, `sh:maxCount 1`, `sh:Violation` — and `coverage.ttl` already declared the range. `sh:name` follows clinical's `"Source Record ID"`, which is also the property's own `rdfs:label`; health's five copies read `"Source Record Identifier"` and the two spellings were never reconciled. No `minCount`: a plan sourced from patient self-report has no originating record to name.

**No gate in this repository could have caught it, and that is the finding.** All three shape checks are class- or entailment-level. `check-class-coverage.py` comes closest and still cannot see it: `coverage:InsurancePlan` *is* shaped, so the class passes while one of its fields goes unjudged. A predicate-level equivalent — every declared property is named by some `sh:path`, against a baseline that can only shrink — is the check this release argues for and does not write.

**Two neighbouring gaps are left open on purpose, and named here so they stay visible.** `cascade:sourceRecordId` (in `core.ttl`) has the identical defect — declared, shaped nowhere — and is live *today* on a VALID conformance fixture, `fixtures/core/source-identity-namespace.VALID.ttl`, where a shaped `health:LabResultRecord` carries it. Of the four namespaced spellings of this one concept, two were unjudged and this release fixes one. Separately, `coverage:ClaimRecord` and `coverage:BenefitStatement` are `owl:Class` with no `rdfs:subClassOf` at all — alone among coverage's record classes, where `InsurancePlan`, `Deductible`, `CopaySchedule` and `DenialNotice` are `prov:Entity` and `AppealRecord` is `prov:Activity`. Since `check-class-coverage.py`'s population is the PROV chain, the two classes this property was authored for are not merely unshaped, they are invisible to the gate that exists to find unshaped classes, and they are absent from `known-unshaped-classes.json` for that reason rather than by exemption.

**Compatibility.** Not widening, and deliberately so: records move from unexamined to examined, so a malformed one can now be rejected. It cannot reject a record that was conformant — every pod record carrying this property carries exactly one `xsd:string` value. Verified locally with pyshacl 0.30.1: two values report `sh:MaxCountConstraintComponent` on `coverage:sourceRecordId` where the shapes at `main` reported `conforms: true`, a non-string reports `sh:DatatypeConstraintComponent`, one value and no value both conform, and `coverage-001`'s expected output still conforms. `spec` runs no validator in CI, so the durable form of that is a negative fixture in `conformance`, recorded in the ledger.

## 2026-08-30: A class nobody was checking, and the process that let it go unchecked (clinical v1.18, v1.19, core v3.9)

One deprecation, followed all the way down. `clinical:CoverageRecord` was superseded by `coverage:InsurancePlan` and retained for EHR-imported data, and six months later nothing anywhere judged it, nothing tracked that fact, and no rule existed that would have noticed. Four changes, in the order the problem is actually shaped: the missing shape, the missing check, the missing process step, and the missing ledger row.

**A retained class with no shape is worse than a deleted one.** `clinical:CoverageRecord` was the only deprecated class in this repository targeted by no `sh:targetClass`, so every record in the spelling all pre-migration coverage data uses reported `conforms: true` — a verdict earned by nothing having looked. clinical v1.18 adds `clinical:CoverageRecordShape`. This is deliberately **not** a widening change: records move from unexamined to examined, so a malformed one can now be rejected. That is the point of it. clinical v1.13 deprecated four classes on identical "retained, still the sole emitter" reasoning and all four kept their shapes; this one never had one to keep.

**A shape for retained data judges the data that was written, not the data the vocabulary describes.** The shape mirrors `coverage:InsurancePlanShape` except in two places, each argued at the constraint. `clinical:effectivePeriodStart` and `effectivePeriodEnd` accept `xsd:dateTime` alongside their declared `xsd:date` range, because the importer emitted midnight-UTC placeholders; the declared range is deliberately left alone, since correcting a range is a vocabulary change with its own bump and sync behind it and a shape must not do that quietly. `clinical:relationship` enumerates this vocabulary's five values rather than the seven-code HL7 SubscriberPolicyholder set coverage v1.4 completed, because no record in this spelling can carry the two codes it never accepted.

**`check-shape-targets.py` reported PASS 3/3 straight over the gap, and was right to.** Its T assertion is conditional by design — it fires only for a superclass some shape already targets — and nothing targets `prov:Entity`, which is what almost every record class here descends from. So `scripts/check-class-coverage.py` asks the different question: every class declaring `rdfs:subClassOf prov:Entity` or `prov:Activity` must be named by some `sh:targetClass`. It found 34 besides the one just fixed, including `clinical:ImagingStudy`, `clinical:ImplantedDevice` and `clinical:MedicationAdministration` — all added in clinical v1.7 with properties and never shaped — the whole `diabetes:` draft namespace, and two `coverage:` placeholder classes whose properties are still deferred. `scripts/known-unshaped-classes.json` records them individually attributed and ratchets both ways: an unlisted unshaped class fails, and a listed class that has since been shaped fails too, so a fix cannot be silently re-absorbed. One entry is flagged as probably the wrong diagnosis: `cascade:DataProvenance` is the classification whose *individuals* are the provenance values, so nothing is ever typed with it and its `prov:Entity` superclass is the thing to revisit rather than the missing shape. The suite's defining control removes the shape v1.18 just added and requires the check to name the class, which is the only assertion that proves it would have caught the live defect. Three shape checks now gate this repository and none can see the others' defect.

**The sequence in `CONTRIBUTING.md` contained the word "deprecat" zero times.** Every obligation was phrased as an addition, so a deprecation could pass all seven steps with every downstream repository still writing the deprecated term and every box ticked. The new "Deprecating a spelling" subsection states the rule the rest follows from — reading and writing move in opposite directions, a deprecated spelling stops being written at once and stays readable indefinitely because a pod is not migrated by a release note — and cites `sdk-typescript`'s `DEPRECATED_TYPE_ALIASES` as the reference implementation, which does exactly this for clinical v1.13's four classes and was never extended to this one. Step 1's shapes obligation, previously "if classes or properties were added", is now unconditional for any class that remains instantiable: that sentence is what excused `CoverageRecord` for six months.

**One of the three departures was not a departure, it was a failure to look.** v1.18 left `clinical:coverageType`'s value unconstrained, reasoning that the property's `rdfs:comment` (`medical`/`dental`/`vision`/`prescription`/`mental_health`) and the corpus (`primary`) disagreed and neither could be preferred without evidence. The evidence was already here. coverage v1.4 ratified a value set for this exact field, argued from the FHIR binding strength, and it lists `primary` **by name** as a retained Cascade value; of the comment's five values, `medical`, `prescription` and `mental_health` are accepted nowhere in this specification — not by FHIR's value set, not by any shape, not by any other ontology. v1.19 therefore adds `clinical:CoverageTypeVocabularyShape` carrying coverage v1.4's list unchanged, at `sh:Warning`, split out so the requirement and the recommendation can hold different severities. The two properties are the deprecated and current spelling of one field and are now judged identically, which is the point. The `rdfs:comment` is left standing and wrong, contradicted by a shape: correcting the prose is a term change and belongs to a release making one.

**Writing the check turned up a false claim in `core`, so that is corrected too.** `cascade:DataProvenance` declared `rdfs:subClassOf prov:Entity` — which in this specification asserts that instances of a class are stored record data. It is a classification, the code list `cascade:dataProvenance` ranges over, so the claim was false of it and, by inheritance, of all ten value terms beneath it. Across the reference patient pod those terms appear 179 times, every one as the *object* of `cascade:dataProvenance` and not once as a type. Nothing measured the claim until this release's check began reading it, at which point all eleven were reported unshaped and written into the baseline as debt that could never be discharged: a code-list member has nothing for a shape to constrain. core v3.9 drops the axiom and the eleven entries go with it, returning the baseline to the 34 it held before the scope widening — so that widening's net growth is zero and every remaining entry is a class that genuinely wants a shape. `cascade:dataProvenance`'s `rdfs:range` is unaffected and still true; the ten terms keep their declarations and `owl:disjointWith` axioms; no shape constrains on `prov:Entity` and the three `sh:in` enumerations match on IRI, so no record changes verdict. Whether these terms should be `owl:Class` at all rather than `owl:NamedIndividual` is a larger question this deliberately does not reopen.

Also: core v3.8 shipped with no changelog entry at all, noticed while authoring 3.9. It is reconstructed from the release commit rather than from memory, and labelled as reconstructed.

It records that the `DEPRECATED (v1.5+)` label cannot be right as written — clinical v1.5 *added* the class, and `coverage:InsurancePlan` did not exist until coverage v1.0 eight days later — so the label was applied by a later edit the squashed history cannot date. `conformance`'s `coverage-001` was migrated while this branch was in flight (PR #4, merged 2026-08-31), which closes that box and opens a smaller one: no fixture now asserts `clinical:CoverageRecord` at all, so the shape this release adds is exercised by nothing and wants a deliberately retained legacy-read fixture. `sdk-typescript`'s `TYPE_MAPPING` remains open with its issue linked; `cascade-cli` owes a shapes re-sync now triggered by this bump. `sdk-python`, `cascade-agent` and the documentation site were **not examined** and are recorded as unknown rather than clear, because an unticked box should mean someone looked.

## 2026-08-28: A warning that was being published as a rejection (clinical v1.17, coverage v1.6)

Two value-set corrections and the check that would have caught the first one. No term is added, removed or renamed anywhere in this release; every change is to SHACL, and both are in the widening direction.

**A `sh:Warning` inside a shape that something reaches by `sh:node` is delivered to the reader as a `sh:Violation`.** SHACL defines conformance as an [empty validation result](https://www.w3.org/TR/shacl/#conformance-checking), and that definition does not consult severity. A nested Warning is still a result, so the value node does not conform, so the referring `sh:node` constraint fires — at its own severity, which is `sh:Violation` unless something declares otherwise. clinical v1.16 put the `clinical:status` and `clinical:documentReferenceStatus` value sets at `sh:Warning` on `clinical:ClinicalDocumentShape`, which is exactly the shape the six document subtypes reach through `sh:node`. The ratchet the release had just written down therefore held for `clinical:ClinicalDocument` and was inverted for `clinical:LaboratoryReport`, `clinical:ProgressNote`, `clinical:DischargeSummary`, `clinical:ConsultationNote`, `clinical:ImagingReport` and `clinical:VisitSummary`: an out-of-set status *rejected* the record. On `clinical:ProgressNote` the underlying warning was not reported at all, only an opaque `sh:NodeConstraintComponent` naming no field, so a reader could not tell what was wrong. Two independent engines agreed.

**The fix is a target set, not a severity declaration.** Declaring `sh:severity sh:Warning` beside the `sh:node` reference is the obvious move and the wrong one: severity attaches to a shape rather than to one nested result, so it demotes the *whole* referenced shape — a discharge summary missing `clinical:sourceEHR` would stop being rejected too. Instead the two bindings move onto `clinical:DocumentStatusShape` and `clinical:DocumentReferenceStatusShape`, which reach all seven document classes by `sh:targetClass`, and `clinical:ClinicalDocumentShape` is left carrying Violation-severity constraints only, which is what makes it safe to reference. The value sets, messages and severities are otherwise unchanged, and a structurally invalid document still fails exactly as before. One shape covers all seven classes rather than a per-class split, because SHACL class targets follow `rdfs:subClassOf*` wherever the axioms are present in the validated graph: a second shape binding `clinical:status` to `clinical:LaboratoryReport` alone reports the same field twice under a validator that loads them and once under one that does not. That was measured during the fix, not assumed, and it is the constraint anyone narrowing these bindings to `composition-status` later will have to work within.

**The class was invisible to every existing check, so there is now a check.** `scripts/check-nested-severity.py` fails any `sh:node` or `sh:qualifiedValueShape` reference into a shape carrying `sh:Warning` or `sh:Info`, against a baseline that can only shrink. It is deliberately independent of `check-shape-targets.py`: one reasons about entailment and the other about severity, and neither can see the other's defect. The baseline records 23 pre-existing sites in `checkup`, `health` and draft `genomics`; the six clinical sites this was written for are fixed rather than baselined. Its own regression suite reintroduces the v1.16 authoring into a scratch copy and requires a named failure, checks that `sh:Info` escalates the same way, checks that a severity declaration on the reference does *not* silence it, and tests the baseline in both directions.

**Fixing the shapes exposed an unsound assertion in the existing check, so that is fixed too.** `check-shape-targets.py`'s assertion **I** asked, per (class, superclass) pair, whether *some* shape targeting the class reached the superclass's constraints. That was sound only while each class had one shape. Publishing a soft constraint on a shape that targets the whole document family — which is what S5 forces — gives these classes two shapes each, and the pair-level question was then satisfied by the new status shape while saying nothing about whether `clinical:ClinicalDocumentShape`'s constraints still reached the subtypes. Deleting a subtype's `sh:node` reported PASS. The assertion is now evaluated per shape targeting the superclass and follows `sh:node` transitively; it examines 26 cases where it examined 14, and the negative control that deletes `clinical:ProgressNoteShape`'s `sh:node` bites again. That control is what caught this, which is the argument for keeping negative controls in the first place.

**An insurance card is a photograph before it is data.** `coverage:InsurancePlanShape`'s `cascade:dataProvenance` value set gains `cascade:AIExtracted`. This is a behaviour change: a plan record carrying that provenance was rejected at `sh:Violation` and now validates. The class has existed since core v3.3 and every clinical and health record shape accepted it from clinical v1.9; this one shape was missed, which left the record type most likely to arrive through a document-extraction pipeline unable to say so.

Also: `coverage.shapes.ttl`'s header had said `1.0 (Phase 4, 2026-02-18)` through two subsequent revisions, because no gate reads shapes-file headers; it now states 1.3 and says why it drifted. The clinical v1.16 prose counted its encounter group as nine terms in three places while the group is eleven (ten properties and `clinical:EncounterParticipant`) — which is what makes that release's own total of fifteen add up. Corrected in `CHANGELOG.md`, `clinical.ttl` and `clinical.shapes.ttl`.

## 2026-08-27: The fields a conformant export sends and a Pod had nowhere to keep (core v3.7, health v2.8, clinical v1.16, coverage v1.5)

A field-coverage measurement against real R4 exports produced one finding in many places: the transport was not thin, the vocabulary was. Twenty-four terms are added here, and each one is a source element that a conformant server sends and that this specification gave an importer no way to record. Every term cites the FHIR R4 element it mirrors by canonical URL, and where a standard already answers the modelling question it is followed rather than improved on. Nothing in this release is invented except where nothing exists to defer to, and each of those is argued at the term.

Additive and strictly widening throughout. Every graph that validated before validates now, and the only new findings on predicates that existing pods already carry are at `sh:Warning`.

**A visit had one field for its name, its reason, and everyone who was in the room.** `clinical:Encounter` carried a class code, a status, a type, two dates, a facility and one provider name. FHIR R4 Encounter carries considerably more, and US Core marks much of it Must Support. Eleven terms close the gap — ten properties and one class. `clinical:encounterReason` takes [`Encounter.reasonCode`](https://hl7.org/fhir/R4/encounter-definitions.html#Encounter.reasonCode) — why the visit happened, in the chart's own words, repeatable because the source element is. `clinical:admitSource` and `clinical:dischargeDisposition` take the two [`Encounter.hospitalization`](https://hl7.org/fhir/R4/encounter-definitions.html#Encounter.hospitalization) fields, which are the only structured signal separating an admission from an office visit. `clinical:encounterClassDisplay` and `clinical:encounterClassSystem` restore the other two members of the [`Encounter.class`](https://hl7.org/fhir/R4/datatypes.html#Coding) Coding: the code stays where it is, because round-trip export needs it, but `Encounter.class` is bound only extensibly, so a server may send a local code, and a local code with no display and no system is both unreadable and unmappable.

**Participation is a structure in FHIR, and it is a structure here.** The remaining five encounter properties plus one class model [`Encounter.participant`](https://hl7.org/fhir/R4/encounter-definitions.html#Encounter.participant): `clinical:EncounterParticipant`, `clinical:hasParticipant`, `clinical:participantName`, `clinical:participantRole`, `clinical:participantRoleCode` and `clinical:participantSpecialty`. FHIR models participation as a repeating BackboneElement carrying a role *and* an individual, and US Core marks the element, its type and its individual all Must Support. The alternative considered and rejected was a flat family of role-qualified predicates on the encounter — an attending name, a referrer name, and so on. It fails on both axes of real data: the role vocabulary is [extensible](https://hl7.org/fhir/R4/valueset-encounter-participant-type.html), so a fixed family of predicates silently drops the local roles a server may conformantly send, and a visit routinely carries two participants in the *same* role, which one-predicate-per-role cannot represent without reintroducing the single-value loss it was meant to fix. A name stored with no role attached is not a smaller fact than a name with one; it is a fact a reader cannot tell is wrong. Specialty is recorded on the participation rather than on a person because in FHIR it is a property of the role: [`PractitionerRole.specialty`](https://hl7.org/fhir/R4/practitionerrole-definitions.html#PractitionerRole.specialty), and it is the specialty the clinician acted in on this visit that describes the visit.

**One predicate was holding two identifier spaces, and a reader could not tell which.** FHIR distinguishes [`Resource.id`](https://hl7.org/fhir/R4/resource.html#id), the server-assigned logical id, from [`.identifier`](https://hl7.org/fhir/R4/datatypes.html#Identifier), the business identifier the source publishes for the real-world thing — for an encounter, the visit or contact serial number US Core marks Must Support. The two do not join: the same string in the two spaces means nothing in common. New `clinical:businessIdentifier` is domain-free and repeatable, because `.identifier` is 0..\* on every FHIR resource, and where the source states a system the value is written in the ratified `{system}|{value}` [token form](https://hl7.org/fhir/R4/search.html#token) so that two transports are comparable without a side table. `clinical:sourceRecordId` keeps its meaning exactly and now states it. **Migration:** a converter that has been writing a business identifier to `clinical:sourceRecordId` must move it. The two predicates are not interchangeable, and a consumer cannot repair the confusion after the fact.

**A document has two statuses and two attributions; each pair had one predicate.** [`DocumentReference.status`](https://hl7.org/fhir/R4/documentreference-definitions.html#DocumentReference.status) (current | superseded | entered-in-error) says whether the pod's *pointer* is current; `docStatus` says whether the *content* is final. Sharing one predicate is not merely lossy: `entered-in-error` is in both value sets and means the reference was filed in error in one and the clinical content is repudiated in the other, so the ambiguity lands precisely where it costs most. New `clinical:documentReferenceStatus` carries the first; `clinical:status` keeps the second. On the attribution side, `clinical:authenticatorName` takes [`DocumentReference.authenticator`](https://hl7.org/fhir/R4/documentreference-definitions.html#DocumentReference.authenticator) — who *signed* a note, routinely not who wrote it, and the part of a note that carries clinical and legal weight — and repeatable `clinical:documentAuthorName` takes `DocumentReference.author` 0..\*, because `clinical:providerName` is `sh:maxCount 1` on the document shapes and every author after the first was being discarded. `Composition.attester`'s mode and time are deliberately not modelled: DocumentReference, which is what both import paths actually read, carries neither, and a predicate whose only possible value would be invented is worse than its absence.

**A status nothing checked, on five record types.** `clinical:status` is written onto lab results, vital signs, documents, laboratory reports and allergy records, and no shape declared it on any of them, so the per-class FHIR value sets were unenforced and validation passed in silence. Each shape now binds the value set its source resource binds, verbatim: `Observation.status` (8 codes) for lab results and vital signs, `DiagnosticReport.status` (10) for laboratory reports, `AllergyIntolerance.clinicalStatus` (3) for allergies, and for the base document shape the ten-code set — because `clinical:LaboratoryReportShape` reaches that shape through `sh:node`, `composition-status` is a strict subset of `diagnostic-report-status`, and the wider set is therefore the only one correct for every class beneath it. The allergy set is three codes and not four on purpose: `entered-in-error` belongs to the verification axis, and admitting it beside `inactive` and `resolved` would merge "the patient no longer reacts to this" with "this allergy was never real", which is the one pair a safety-relevant record must never conflate. All five are `sh:Warning`, per the ratchet [core v3.5](#2026-08-09-a-records-source-identity-is-declared-canonical-and-never-the-transport-core-v35) wrote down: a value existing data carries is reported, never rejected, and the severity is raised only after a release in which the warning is observably absent from conforming output.

**Two domains said something the data has never been.** `clinical:providerName` declared `rdfs:domain clinical:CoverageRecord` while being written on every clinical record type, and `clinical:verificationStatus` declared `rdfs:domain clinical:Condition` while FHIR carries `verificationStatus` on `AllergyIntolerance` as well. Both domains are dropped rather than widened to a union, following the v1.11 treatment of `clinical:indicationReference`: a union on a cross-class predicate makes a reasoner infer that an allergy record is a Condition. Where the same predicate binds to different value sets on different classes — and the allergy verification set has no `provisional` and no `differential`, because a differential diagnosis is not a thing one has about an allergy — that is a SHACL job, and it is now done in SHACL. No shape ever encoded either domain, so no pod is affected.

**One property is deprecated, and it is the one nothing was using.** `clinical:observationStatus` was defined in v1.4 with `rdfs:domain clinical:LabResult`, a class deprecated in v1.13 that no import path emits; it is bound by no shape and written by no converter. It is retired rather than re-domained, because re-domaining it onto the class that *is* emitted would give an Observation-derived record two status predicates with one FHIR element behind both — the exact ambiguity this release exists to remove. Retained, not removed, on the same terms as the v1.13 class deprecations: any pod carrying it stays valid and readers must continue to accept it.

**A coverage record could not say whether the plan was in force.** `coverage:InsurancePlan` had no status property at all, so an importer reading a conformant Coverage resource had to discard the one element FHIR requires it to carry. `coverage:claimStatus` and `coverage:adjudicationStatus` were never substitutes: they belong to the denial and appeal workflow and describe a claim. New `coverage:status` takes [`Coverage.status`](https://hl7.org/fhir/R4/coverage-definitions.html#Coverage.status), required binding to `fm-status`: active | cancelled | draft | entered-in-error. FHIR marks it a modifier element, which is why this is not a nice-to-have — a cancelled plan read as an active one is a wrong answer to "am I covered", not a missing one. The value is a `sh:Violation` because the binding is required and no pod has ever carried the property; its *presence* is deliberately not required yet, because no producer has had the chance to write it.

**Attachments: a Pod can now hold the documents its records point at.** A `DiagnosticReport` that says "the report is at this URL" stops being answerable the moment the URL stops resolving. FHIR permits bytes either inline as base64 (`Attachment.data`) or by reference (`Attachment.url`), and core v3.7 takes the second, for a reason specific to Pods rather than to messages: Turtle files here are parse-critical, read in full by every consumer to answer any question, so an unbounded base64 literal is paid for by every reader including the ones that will never open the attachment. Bytes live under `attachments/{algorithm}/{digest}`, and the Turtle carries a small `cascade:Attachment` node with the media type, the digest, the algorithm and a pod-relative path. The file's name *is* its digest, which is what makes the arrangement checkable rather than merely tidy: a consumer hashes what it read and compares it with where it read it from, so nothing has to be trusted to keep name and content in agreement, and both cross-source deduplication and idempotent re-import follow with no mechanism behind them. FHIR's `Attachment.hash` is deliberately not followed — it fixes SHA-1, which is collision-broken, and a collision in a content-addressed store is a mechanism by which one document silently replaces another — so the algorithm is named explicitly from the [RFC 6920](https://www.rfc-editor.org/rfc/rfc6920) registry and `sha-256` is required of new implementations. Encryption at rest and sync behaviour for the directory are implementation-defined in this release, stated so that their absence is a decision.

Twenty-four terms in all: 15 in `clinical:` (14 properties and 1 class), 8 in `cascade:` (7 properties and 1 class), 1 in `coverage:`; `health:` adds no term and gains three shape bindings. `pod-structure.md` goes to 1.1 with a new section 4.3 and a new file-naming section 7.5.

Tags (applied after merge): `vocab/core-v3.7`, `vocab/health-v2.8`, `vocab/clinical-v1.16`, `vocab/coverage-v1.5`. Per-vocab detail is in `ontologies/core/CHANGELOG.md` and in the inline changelogs of each `.ttl` and `.shapes.ttl`.

## 2026-08-20: Draft vocabularies carry per-term maturity (advisory, diabetes, evidence, genomics, workbench)

Cascade stated maturity once per vocabulary, in prose a machine could not read: an ontology-level `owl:versionInfo "1.0-draft"` and an `rdfs:comment` saying the vocabulary is subject to change. That tells a consumer nothing about which individual terms are settled, so the only safe reading of a draft vocabulary was to treat all of it as provisional, including the parts that had not moved in three revisions.

The ratified answer already exists and is not ours. [W3C SemWeb Vocabulary Status](http://www.w3.org/2003/06/sw-vocab-status/ns#), which originated in FOAF, defines `vs:term_status` with four values: `unstable`, `testing`, `stable`, `archaic`. Its own description states the design reason for the granularity, that indicating status at the term level rather than the vocabulary level makes fine-grained improvement easier. That is exactly the guarantee a `/v1#` namespace makes: the vocabulary evolves in place, and a term is promoted without minting a new namespace. This repository already used the matching standard at the other end of the lifecycle, `owl:deprecated`, 21 times.

All 411 terms across the five draft vocabularies now carry `vs:term_status`. Terms are `unstable`, which is what a draft term is; the five terms already marked `owl:deprecated` are `archaic`. No term definition, domain, range, label or comment changed, and no triple was removed: the annotation was verified by diffing the parsed N-Triples of every file before and after, which must show the added status triples and nothing else.

**The status is per term precisely so it can stop being uniform.** A blanket `unstable` across a draft vocabulary carries no more information than the prose it replaces. What it buys is the mechanism: promoting `evidence:Assertion` to `testing` is now a one-triple change a consumer can query, rather than a graduation event for the whole vocabulary. Vocabularies should promote terms as they settle, and the value of this change is only realised when they do.

`owl:versionInfo` remains the vocabulary-level draft marker and is unchanged in meaning. The two answer different questions, and where both speak they must agree: a term marked `owl:deprecated` must be `archaic`, which `scripts/check-term-status.py` enforces, because two machine-readable maturity signals that contradict each other are worse than one.

The check is gated in CI with negative controls, for a specific reason. The pass that added these annotations silently skipped 96 of 411 terms, every term that happened to be preceded by a section comment, and reported success. It was caught by auditing the parsed graph, never by the inserter's own count. A tool's report of what it did is not evidence that it did it.

Also corrected here: `rdfs:seeAlso` on `advisory`, `diabetes` and `genomics` pointed at documentation paths (`/docs/advisory/v1.0-draft/`, `/docs/diabetes/v1.0-draft/`, `/docs/genomics/v1/`) that were renamed away and had been returning 404. All five drafts now point at their published `/docs/{vocab}/v1-draft/` page.

Per-vocab: advisory 1.0-draft.0.2, diabetes 1.0-draft.0.2, evidence 1.0-draft.0.3, genomics 1.0-draft.0.5, workbench 1.0-draft.0.7. None of these vocabularies is in `VOCAB_VERSIONS`, so no downstream version registry changes.

## 2026-08-14: Four rulings — check the unchecked, keep what was dropped, canonicalize identity inputs (core v3.6, health v2.7, clinical v1.15)

Four independent findings, authored together because three of them touch the same two property shapes and the fourth is what makes those shapes reachable by real converted data. All of it is additive and strictly widening: every graph that validated before validates now, at the same severity, with one deliberate new finding at `sh:Warning` only.

**A vital sign's interpretation was unchecked, and is now checked at Warning.** The v2.6/v1.14 alignment put the 60-value HL7 ObservationInterpretation `sh:in` on the LAB shapes and left `clinical:VitalSignShape` with `sh:datatype` and `sh:maxCount` and no value set, so the identical predicate was validated on a lab result and not on a vital sign. That gap was recorded as intentional because emitted vital data uses `elevated`, which is in neither ratified set, and a Violation would have rejected records that already exist. That reasoning justifies not making it a Violation; it never justified leaving the property unchecked. The binding is applied at `sh:Warning`, which is the ratchet [core v3.5](#2026-08-09-a-records-source-identity-is-declared-canonical-and-never-the-transport-core-v35) wrote down for exactly this case: a value existing data carries is reported, not rejected, and the severity is raised to `sh:Violation` in a later version only after a release in which the warning is observably absent from conforming output. `health:` gains no matching constraint, and that is not an oversight: `health:interpretation`'s domain is `health:LabResultRecord`, and `health:DailyVitalReading`, the only vital class the health vocabulary defines, carries no interpretation predicate at all, so a shape there would constrain a triple no conforming record can write.

**An identifier hashed over an unordered field is not an identifier.** health v2.6 and clinical v1.14 made four code fields 0..\* to match [`CodeableConcept.coding`](https://hl7.org/fhir/R4/datatypes.html#CodeableConcept). An implementation that derives a record's identity from its content then hashes a field that may hold several values, and without a canonical form two exports of the same record that list the same codings in a different order mint two different identifiers and the record silently splits in two. The canonical form is now stated normatively on `cascade:cascadeUri` in `core.ttl`: discard empty members, deduplicate, sort by Unicode code point, join with a fixed separator (U+002C recommended, and required of new implementations). Three invariants are normative independently of the separator, and they are what the conformance vectors check: shuffling members must not change the identifier, a one-value field must mint the same identifier whether spelled as a scalar or a one-element sequence, and repeating a member must not change the identifier. Scalar agreement is what keeps every identifier written before those fields became repeatable exactly where it is.

The scope limit is as load-bearing as the rule. It governs identity inputs whose source element is a SET. It must never be applied to an input whose source order carries meaning — FHIR `name[0]` is the primary name, and a component or note list is a sequence — because sorting there merges records the source deliberately distinguished. An implementation that already ships a different fixed separator keeps it; changing a separator re-mints every identifier the site ever produced, which is precisely the harm the rule exists to prevent.

**Four ways of saying "missing" stopped collapsing into one blank.** A C-CDA document distinguishes `nullFlavor="UNK"` (a value applies, nobody knows it), `NAV` (we will know later), `NASK` (nobody asked) and `ASKU` (we asked, the patient did not know). An importer that drops all four writes one indistinguishable blank, and a reader can no longer tell a test that was never ordered from one whose result is pending. Two ratified code systems already draw the distinction, so none of this is invented: [HL7 v3 NullFlavor](http://terminology.hl7.org/CodeSystem/v3-NullFlavor) (OID 2.16.840.1.113883.5.1008) is what C-CDA writes, and [FHIR data-absent-reason](http://terminology.hl7.org/CodeSystem/data-absent-reason) is the harmonized flat set FHIR R4 binds `Observation.dataAbsentReason` to. Cascade binds to data-absent-reason: it is already the code system this vocabulary cites, its 15 codes are all selectable where v3-NullFlavor marks UNK, NI, OTH and INV abstract, and FHIR is the transport both converter paths read. New `cascade:dataAbsentReason` carries why a record's primary VALUE is absent, with FHIR's exact semantics and the full nullFlavor mapping table stated on the property. Separately, both interpretation value sets gain the fourteen data-absent-reason codes they did not carry, because putting a data-absent-reason coding into the CodeableConcept that is missing is FHIR's own idiom for an element absent for a stated reason, and accepting only `unknown` made every reason the same reason.

**A source code that fits no value set is kept rather than dropped.** New `health:interpretationSourceCode` and `clinical:interpretationSourceCode` carry the source's verbatim interpretation code, written only when that code is a member of neither bound value set. A laboratory's local abnormality flag is the ordinary case. The alternative considered and rejected was accepting the loss with a warning: a closed value set plus a lossy importer means such a flag is either dropped on the floor or written into a field that then fails validation, and in both cases the Pod can no longer answer what the source actually said. The property is deliberately unconstrained — no value set, no pattern, no case folding — because constraining a verbatim carbon copy recreates the loss it exists to prevent. The pair is what makes the vital-sign migration lossless: `interpretation "H"` states the ratified reading and `interpretationSourceCode "elevated"` keeps what the source wrote.

**A procedure was failing for missing a name it was carrying.** A C-CDA import path writes the procedure name to `health:procedureName`, a predicate the health vocabulary does not define, on records it types `clinical:Procedure`. So every converted procedure failed `clinical:ProcedureShape`'s name requirement as though it had no name, and carried its name on a predicate no shape targets, so the name itself was validated by nothing. Measured 2 of 2, 7 of 7 and 1 of 1 across three public sample documents. This is resolved in favour of `clinical:procedureName` rather than by blessing the health: spelling: there is no health-namespace procedure vocabulary at all, so ratifying the emission would mint an undefined-term family of the kind health v2.5 spent a release eliminating; the record is typed `clinical:Procedure`, so a health: name on it is a namespace mismatch inside one record rather than a coherent alternative serialization; and this repository's one dual-spelling precedent, `health:DailyVitalReadingShape`'s `sh:or` over `cascade:date` and `health:date`, exists because both serializations are live and defined, which is not the case here.

`clinical:ProcedureShape`'s name requirement therefore becomes an `sh:or` over both spellings, so a Pod already holding the health: triples stops failing without any data being rewritten, and a new warning-severity `clinical:ProcedureNameSpellingShape` fires wherever the deprecated spelling appears. This is a MIGRATION WINDOW and not a ratified dual: producers write `clinical:procedureName` only, and both the `sh:or` alternative and the warning shape are removed together in a later clinical version once the warning is observably absent from conforming output. A consumer querying `health:procedureName` must add `clinical:procedureName` to its query now.

## 2026-08-09: A record's source identity is declared, canonical, and never the transport (core v3.5)

A Cascade record has always carried two source-shaped properties and needed three. `clinical:sourceEHR` is a display LABEL, worded the way the source document worded it. `cascade:sourceSystem` is the INGESTION batch, which records how and when data entered the Pod. Neither is an origin, and using either as one produces a measurable failure in a different direction.

Keying "are these two records from the same source?" on the ingestion batch answers yes for every pair on a Pod imported under one label, so nothing is ever compared and every duplicate survives; on one real corpus 148 cross-source duplicates were invisible for exactly this reason. Keying on the display label fails the other way: a FHIR export identifies its origin by the registrable domain of its endpoint, and a C-CDA document of the SAME system identifies it by the custodian organization name, so one health system occupies two rows of any source view purely because of which transport the patient happened to download.

**`cascade:sourceIdentity` is the ORIGIN axis.** New in core v3.5, range `xsd:string`, domain `owl:Thing`. Its value is a canonical token that is the same whatever transport carried the record, and it is scheme-prefixed so a consumer can always see how much the producer actually knew: `org:{slug}` when an organization was derivable, `ns:{namespace}` when only an identifier assigning authority was (the FHIR server base URL, or the C-CDA `<id>` root OID), and `transport:{label}` as an honestly-labelled last resort that is explicitly NOT an origin claim. The slug normalization that both transports must implement identically is stated in full on the property in `core.ttl`: reduce an organization name or a registrable domain to its leading distinctive token, dropping generic institution, specialty, legal-form and stopword tokens, so `Meridian Health System` and `meridianhealth.example` both give `org:meridian`, and `Providence Health and Services Washington and Montana` and `providence.org` both give `org:providence`.

**The normalization is deliberately biased toward collapsing.** The two failure directions are not symmetric. Collapsing two different organizations onto one identity suppresses comparisons between their records, so duplicates remain in the Pod, visible and recoverable. Splitting one organization across two identities lets records that organization deliberately kept apart be compared and merged, which destroys content. So regional and specialty qualifiers are dropped rather than being allowed to split a system, and the rule takes the leading distinctive token rather than all of them.

**The other two axes are unchanged, and now say what they are not.** `clinical:sourceEHR` keeps its meaning exactly: a display label, and an application aliases it to the origin rather than reading it as one. `cascade:sourceSystem`'s comment now states that it records how and when data arrived, never where it came from, and must not be used as a reconciliation key. No property was added to, removed from or renamed in any other vocabulary, and no emitted value changes meaning.

**Compatibility: absence is not a finding.** `cascade:SourceIdentityShape` uses `sh:targetSubjectsOf`, so it evaluates only records that already carry the property and reports nothing on a pod written before v3.5. Requiring presence at Warning severity the moment the property is defined would turn every existing pod amber for something no producer had yet had the chance to write, and a warning that fires on correct historical data is one readers learn to skip. The ratchet is written down rather than left to judgement: presence becomes a Warning on the `health:` and `clinical:` record shapes once the reference producers emit it, and a Violation only after a release in which that Warning is observably absent from conforming output. Each step is its own vocabulary version.

Tag (applied after merge): `vocab/core-v3.5`. Per-vocab detail is in `ontologies/core/CHANGELOG.md` and in the inline changelog of `core.ttl` and `core.shapes.ttl`.

## 2026-08-08: Align lab, code and date constraints to ratified standards (health v2.6, clinical v1.14, coverage v1.4, checkup v3.3)

Real-world Epic FHIR exports, and C-CDA documents through the same pipeline, were failing `cascade validate` on records that are correct at source. Every failure traced to a Cascade constraint that was narrower than the standard it claimed to describe. This release replaces invented value sets with ratified ones and invented cardinalities with the source resource definitions, and shapes a class that had no shape. Shapes and JSON-LD contexts only: no class or property is added, removed, renamed or deprecated, and apart from the new Encounter shape the change is strictly widening.

**Interpretation is now HL7, not Cascade.** `health:interpretation` and `clinical:interpretation` were constrained to five words this project made up (normal, high, low, abnormal, critical). Both are now bound to the 49 selectable codes of [`http://terminology.hl7.org/CodeSystem/v3-ObservationInterpretation`](http://terminology.hl7.org/CodeSystem/v3-ObservationInterpretation) version 3.0.0, the code system FHIR R4 binds `Observation.interpretation` to. The eight abstract concepts are excluded because they are hierarchy nodes rather than values; the ten codes the code system marks deprecated are included, because a deprecated code is still a defined code and historical results carry them. A laboratory reporting a susceptibility (S/I/R), detection (POS/NEG/DET/ND/IND), reactivity (RR/WR/NR) or change (B/D/U/W) result was previously rejected for being conformant. The [`data-absent-reason`](http://terminology.hl7.org/CodeSystem/data-absent-reason) code `unknown` is also accepted, for the very common case of a source Observation that carried no interpretation at all. The previous ten words are retained so nothing already written stops validating.

**Multi-valued where FHIR is multi-valued.** `health:labCategory` follows [`Observation.category`](https://hl7.org/fhir/R4/observation-definitions.html#Observation.category), which is 0..\*. `health:testCode`, `health:icd10Code`, `health:snomedCode`, `clinical:snomedCode` and `clinical:icd10Code` follow [`CodeableConcept.coding`](https://hl7.org/fhir/R4/datatypes.html#CodeableConcept), which is 0..\*. Dual-coded problem-list entries and multi-coding lab observations are the normal shape of EHR output, not an anomaly, and `sh:maxCount 1` was rejecting records for preserving what the source sent.

**Codes keep their own format rules.** No `sh:pattern` was added to any code property, and one was corrected. SNOMED CT identifiers are 6-18 digit integers and ICD-10-CM permits a letter in any character position, so a lexical pattern on those buys nothing and costs valid codes. Two patterns that did exist were wrong: `checkup:icd10Code` required digits in the second and third characters, which rejects every code under live categories such as C4A, D3A and M1A (the ICD-10-CM Official Guidelines for Coding and Reporting, Section I.A.2: "Characters for categories, subcategories and codes may be either a letter or a number"); and `clinical:cptCode` required five digits, which is CPT Category I only and rejects Category II (four digits + F), Category III (four digits + T) and Proprietary Laboratory Analyses (four digits + U) codes.

**Insurance follows the FHIR bindings.** `coverage:subscriberRelationship` held five of the seven codes in [`subscriber-relationship`](http://terminology.hl7.org/CodeSystem/subscriber-relationship); `common` and `injured` were simply missing, so a conformant export warned. `coverage:coverageType` enforced a closed four-member enum at Violation severity on an element FHIR R4 binds [extensibly](https://hl7.org/fhir/R4/terminologies.html#extensible), where alternate codes MAY be used; presence stays a Violation, and the value is now checked at Warning against the FHIR value set plus the four retained Cascade values.

**Dates may be date-precision.** FHIR's `dateTime` primitive is explicitly partial-precision, "YYYY, YYYY-MM, YYYY-MM-DD or YYYY-MM-DDThh:mm:ss+zz:zz" ([datatypes](https://build.fhir.org/datatypes.html)), and C-CDA `effectiveTime` commonly carries a calendar day with no time. Date properties whose value is CARRIED OVER from a source document (`clinical:encounterDate`, `clinical:documentDate`, `clinical:onsetDate`, `clinical:procedureDate`, `health:performedDate`, `health:reportedDate`, `health:onsetDate`, `health:administrationDate`) now accept `xsd:date` alongside `xsd:dateTime`, and their JSON-LD terms no longer coerce to `xsd:dateTime`, so a producer states the precision it actually has instead of inventing a midnight. Timestamps Cascade itself generates (`clinical:importedAt`, statistic period bounds, derived episode dates) are unchanged and still require `xsd:dateTime`.

**Encounters are validated at all.** `clinical:Encounter` has been defined since clinical v1.7 and targeted by no shape, so validating an encounter evaluated zero constraints and returned PASS. New `clinical:EncounterShape` and `clinical:EncounterTemporalShape` constrain cardinality, datatype, provenance and the IRI requirement that the `clinical:hasEncounter` edge implies. They deliberately do not constrain what kind of visit an encounter may be: `encounterClass` gets no enum because FHIR binds `Encounter.class` extensibly and servers send either the abbreviation or a display string, and the `encounterStatus` enum is the FHIR R4 `EncounterStatus` value set verbatim at Warning severity. Having a position in time is a Warning, not a Violation, because `Encounter.period` is 0..1.

Tags (applied after merge): `vocab/health-v2.6`, `vocab/clinical-v1.14`, `vocab/coverage-v1.4`, `vocab/checkup-v3.3`. Per-vocab detail is in the inline changelog of each ontology and shapes file.

## 2026-08-03: Validation Profile 1.0 (the entailment regime, stated and enforced)

New normative document `validation/index.md`, plus the check that holds this repository to it. No released vocabulary changes; nothing in `VOCAB_VERSIONS` moves.

**The problem.** SHACL is a validation language, not a validation configuration. [SHACL 2.1.3.1](https://www.w3.org/TR/shacl/#targetClass) resolves `sh:targetClass` over SHACL-instances in the DATA graph, and Cascade pod records carry `rdf:type` triples but no schema axioms. A subclass axiom declared in an ontology file therefore confers no shape coverage on the subclass. A validator that merges ontologies into the data graph before validating sees the opposite, and both readings conform to SHACL. The same file could be valid under one implementation and invalid under another with neither doing anything wrong.

**The rule.** Cascade shapes are entailment-independent. Every class a shape means to constrain carries an explicit `sh:targetClass`; constraint inheritance is stated with `sh:node` or a shared target list rather than inferred; `sh:class` value constraints enumerate the acceptable subclasses. A conforming validator MUST reach a correct verdict with no inferencing, MAY perform entailment as an extension, and MUST get the same verdict either way. A verdict difference between an entailing and a non-entailing validator is a defect in the shapes, not a validator configuration question. A conformance suite must be able to reproduce every fixture's expected outcome with no pre-validation merge. The rejected alternative, mandating an ontology merge, is argued in `validation/index.md` §4: it moves correctness into every consumer's configuration and is unenforceable in a library embedded in someone else's application.

`rdfs:subClassOf` is unaffected and still required for modelling. It is what makes `rdfs:domain` / `rdfs:range` true, and it is what the check reads to work out which classes need an explicit target. It is simply not a validation mechanism.

**The enforcement.** `scripts/check-shape-targets.py` evaluates three assertions over every ontology and shapes file here: target closure (T), constraint-set equivalence (I), and value-class closure (C). It reports how many cases each examined and fails if any examined none, because an assertion with nothing to inspect has established nothing. `scripts/test-check-shape-targets.sh` is its regression suite: every assertion is paired with a scratch copy of the repository carrying a deliberately reintroduced violation that the check must catch and name. New CI job `shapes` runs both on every PR touching `ontologies/`. This is the first automated test of this repository's own shapes.

**Found on the first run, and fixed here:** genomics v1-draft.0.5. `genomics:CopyNumberVariantShape` claimed in its comment to inherit `VariantShape` transitively and did not, so copy number variants were never checked for `genomics:dataQualityTier` (the value the `D-QUALITY-TIER` safety constraint on `VariantInterpretation` is evaluated against) or for carrying a stable identifier. Measured across both engines: the same fixture was reported conforming by a non-entailing validator and non-conforming with two Violation results by an entailing one. Fixed with an explicit `sh:node`, after which both engines agree. `HaplotypeShape`'s `hasComponent` `sh:class` was widened to enumerate `CopyNumberVariant`. See `ontologies/genomics/CHANGELOG.md`.

The released vocabularies (`core`, `health`, `clinical`, `coverage`, `checkup`, `pots`) already satisfy all three assertions and are unchanged. No tag; the Validation Profile carries its own version, as `serialization/index.md` does, and `VOCAB_VERSIONS` records vocabulary versions rather than profile versions.
